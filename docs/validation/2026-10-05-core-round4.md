## Behavior and resource boundaries

Owned PTY adoption retains the source allocator through completion and avoids
the payload copy when CRLF expansion is unnecessary. Inline writes copy into
their request, and expansion allocates the replacement buffer before freeing
the original. Empty, exited, closed, allocation-error, cancellation, and
completion paths consume the owner exactly once. Partial writes retain the
same logical FIFO head. The mailbox fixture checks complete bracketed paste
framing; the separate 64 KiB real-PTY fixture checks binary payload ordering
and original-allocator release. It does not count partial-write callbacks or
manufacture a real kernel cancellation.

This does not establish a total PTY memory bound. Native String/Data,
confirmation previews, C bridge copies, encoding, mailbox payloads, and active
writes need one coordinated byte-credit model. Current clipboard entry points
can materialize a complete object larger than a proposed budget. Lossless
arbitrary input, fixed RAM, and a nonblocking main thread require a stable
streaming source or asynchronous disk staging, with the initial read peak
stated separately. The staging policy remains a user decision in the parent
conversation; a question emitted inside this delegated thread is not evidence
that the user received or approved it. A bounded drain
also needs explicit renotification when messages remain, because libxev drains
Mach notifications before the callback; rearming alone is insufficient.

The recommended next scope is stable pull-sources plus coordinated credits,
while preserving ordinary paste behavior. Current ordinary clipboard reads
materialize full String/Data and cannot simply be labelled streaming. If the
user instead wants arbitrary ordinary paste admitted without main-thread
waiting, the parent must obtain an explicit disk-staging choice and state
that the initial full read remains a separate memory peak; staging alone does
not establish an all-stage hard RAM bound.

Disk staging may write sensitive clipboard content. Its design needs private
access, cleanup on success/cancel/error, crash-residue handling and an honest
statement that unlinking cannot guarantee physical erasure on APFS. Keeping
current behavior avoids new admission semantics but retains unbounded pending
byte growth with a slow child and possible mailbox waits in the submitter.

Kitty's existing source/animation storage limit is independent of encoded and
decompressed loading buffers, renderer RGBA copies, GPU textures, captures,
and background images. The source storage default is 320,000,000 bytes;
single loading allocations allow up to 400 MiB and dimensions up to 10,000.
Background encoded/decoded limits are separate. None of these values is a
process RSS bound. Kitty execution is synchronous at APC completion; there
is no decoder task to cancel. Screen loading ownership is released on close.

The renderer fix uses the existing pending/ready/replacement unload states.
It restores a same-generation image after deferred unload and supports retry
if restoring the CPU pixels fails. CPU captures and generation replacement
are tested; GPU upload and desktop timing are separate integration concerns.

Reflow writes each grapheme directly and grows byte storage only after an
actual allocation failure. Destination pointers are refreshed before retry.
Map capacity checks and unexpected-map exhaustion handling are preserved.
System OOM propagates through existing reflow cleanup; the whole resize does
not gain a transactional rollback guarantee.
Operation probes are per test instance and absent from production storage;
their counts do not represent system allocations or wall-clock speed.

The Quick cache has no production instance. Restore uses terminal tree,
focus, base configuration, position, and size. Its encoded Entry/DisplayEntry
fields and `screenStateEntries` key remain readable, including nonempty
historical archives. Terminal compatibility and accessibility paths are not
removed.

Run three warmups and at least 15 alternating baseline/candidate repetitions

Build those tools through `python3 scripts/build.py core -Demit-bench
-Doptimize=ReleaseFast`. Keep a named copy of each benchmark binary outside
the checkout for alternating measurements; do not overwrite a running build
or run timing comparisons concurrently.

PTY responsiveness follow-up must use the real IO thread and PTY under a slow
reader, then request resize and stop while writes are pending. Record accepted

existing 25 ms resize coalescing interval. A queue-only simulated loop tick
cannot substantiate responsiveness.

## Suggested next batch

1. Resolve the stable-source versus disk-staging policy, then implement total
   PTY byte credits and bounded drain/control fairness together. Expected
   benefit is a real memory bound and predictable control progress under a
   slow child; risk is high because admission, framing, failure delivery and
   close interact. Allow roughly 3–5 days including the real-thread stress
   baseline above. No rejection, truncation or staging behavior is introduced
   in this round.
2. Use the dedicated OSC 8 corpus to evaluate a source-page/link to
   destination-ID mapping during reflow. Reset it when destination storage
   changes and retain reference counts. Eight duplicate calls are proven in
   the controlled fixture; time savings are unmeasured. Risk and effort are
   moderate, approximately 1–2 days with cross-page/growth/OOM regressions.
3. Investigate adopting the PNG decoder output at
   `src/terminal/kitty/graphics_image.zig:657` instead of copying it into
   another ArrayList. This is a visible duplicate buffer path, with unmeasured
   runtime benefit. Confirm allocator and size-limit ownership before any
   change; keep decoding, PNG compatibility and close cleanup intact. Allow
   roughly 1–2 days for allocation-failure and format/capacity regressions.

Do not delete terminal protocol compatibility, grapheme/width mode handling,
Kitty functionality, accessibility semantics, active Swift split trees,
restoration fields, or mailbox/write teardown merely to reduce code size.
Lazy reflow remains a separate design requiring width generations and
pin/selection/search consistency.
