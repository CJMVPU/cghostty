# 窗口锁、输入公平性与按数据决定后续优化

基线为 `2bf0729b0`。本轮按用户确认执行测量、输入与窗口锁调整，以及后续优化取舍。
最终合成、光标/滚动 shader、ScrollScene 纹理结构和固定窗口行为保持原实现。

## 统一的执行边界

- 主线程只在短锁内发布窗口成员和布局；窗口线程取得值快照后在锁外准备与编码。
- 快照保留 Surface 和目标纹理。发布资源时校验成员 token，仅更新纹理缓存，不覆盖新布局。
- Surface 有一个渲染交接 gate：只有窗口线程使用它。主线程只发布期望所属窗口；
  新窗口遇到尚未结束的旧绘制时跳过当前 tick，下一 tick 重试，不新增任务池。
- 移动时在窗口线程切换 core sink，等待旧分屏 GPU 写入结束；旧窗口的提交槽继续持有
  其采样纹理和参与会话直到 GPU 完成。不同窗口使用独立的分屏输出纹理。
- 移除和窗口关闭只发布撤出请求。窗口线程排空 GPU 工作后回收资源；Surface 保留 App，
  因而延迟退役不会让 core app 先于会话销毁。主线程不再同步等待整个窗口 GPU 排空。
- 按键的 KAM、链接刷新、编码模式、清选区/回底部，以及鼠标移动两处终端锁，
  统一使用已有 lockDemand/unlockDemand。它是公平性交接，仍然会等待终端临界区。
- 输入快照、异步输入命令队列、分屏并行调度器均未引入。

## 测量字段

沿用 render-trace 和 summarize-render-trace.py；关闭 trace 时不记录、不启动写线程。
Zig 路径的细分时钟仅开启 trace 时采集；原生窗口保留轻量媒体时钟取样。

| 事件 | 含义 |
| --- | --- |
| window_prepare | 窗口全部分屏准备的墙钟时间、最慢分屏、窗口帧序号 |
| window_lock | 主线程成员/布局锁的等待时间 |
| terminal_lock / input_lock | 帧快照和输入路径等待终端锁的时间 |
| update_lock / frame_slot | 渲染状态 gate 和 GPU 帧槽等待时间 |
| shape | 每次更新的 run 缓存查询数、未命中数、未命中排版总耗时 |
| atlas_grow | CPU 图集扩容次数、耗时与新尺寸 |
| atlas_resize / atlas_upload | 各 GPU 帧槽纹理替换，以及上传耗时和字节数 |
| cf_release_enqueue | 帧末投递 CoreText 释放对象的耗时，含队列等待 |
| input_probe / input_ready / pane_content | 受控输入探针、验证回显后的 PTY 修订号、帧包含的修订号 |

CPU 图集扩容与 GPU 帧槽纹理替换是两类计数，不能混加。墙钟时间包含阻塞，不能视为 CPU 使用率。

输入探针由测试明确发送，随后验证唯一回显标记，再把该 PTY 修订关联到真实显示的窗口帧。
它不会将按键后的第一个光标动画帧误认为回显。日志不记录文字或键码。
探针起点是测试调用输入 API 的媒体时钟，不是硬件按键或 NSEvent 时间，因此指标叫
input_probe_to_content_display_ms，不称为物理输入到发光延迟。

trace 队列沿用非阻塞丢弃策略。汇总包含丢失数、探针数、匹配数与
input_probe_trace_complete；有丢失的记录只能作为观察，不能证明精确首次呈现延迟。
不因测量需要让渲染线程等待磁盘或日志锁。

## 对照方法

旧窗口实现来自 HEAD，在独立临时目录加入相同帧暂停钩子和测量代码，不覆盖工作区。
Zig 侧诊断及 demand 输入锁相同，所以此对照隔离的是窗口锁策略，不能称为输入锁优化前后对照。

- 阻塞回归：明确暂停一帧准备，然后从主线程更新布局、移除分屏并停止窗口。
  3 秒仅是测试死锁保护，实际协调使用信号；要求主线程先返回，再释放准备线程。
- 新实现进一步验证真实视图跨窗口移动、源窗口关闭、目标窗口颜色与 PTY 会话继续工作。
  源窗口必须先显示 PTY 的红色测试画面，不能把首帧空白当作准备完成。
- 输入探针：静止/动画两组各 200 次；原始记录丢失会明确报告，不让正确性依赖遥测无丢失。
- 中英文负载：固定总窗口面积，1/4 分屏各 100 轮，最终回归让不同分屏使用错开的汉字流。
  它是冷字形与连续输出压力，不代表所有日常使用。最初同字形流试跑与最终负载分开记录。

## 实测结果与决定

旧窗口锁在故意暂停帧准备时，主线程操作耗时 **3007.80ms**，阻塞回归按预期失败。
短锁版本的 API 对照为 **0.024ms**；进一步包含真实视图移动、目标窗口创建和源窗口关闭的回归为
**1.68ms**。这是“主线程是否必须等被暂停的帧”验证，不能当作日常输入延迟降低 3 秒。

最终定向压力负载（包含冷启动帧，不丢弃最慢帧）：

| 指标 | 1 分屏 | 4 分屏、错开汉字流 |
| --- | ---: | ---: |
| 窗口准备帧数 | 78 | 86 |
| 帧准备 p95 / 最大值 | 8.06 / 9.12ms | 6.97 / 8.57ms |
| 观察到的超时提交 | 2 | 2 |
| CoreText 未命中排版累计 | 3.54ms | 9.23ms |
| CPU 图集扩容 | 3 次 | 2 次 |
| CPU 图集扩容最大耗时 | 1.34ms | 0.25ms |
| CF 释放投递 p95 | 0.0028ms | 0.0069ms |
| trace 丢失 | 0 | 4 条 |

固定总窗口面积、字体图集共享、可见内容和帧合并数量不同，所以不能用 1/4 分屏耗时的比值计算并行收益。
四分屏记录存在丢失，计数和分位数均为已观测记录；不能宣称没有其他超时。
冷字形负载确有少量超过约 8.3ms 预算的帧，未将其隐藏或宣称 120Hz 全部达标。

取舍：

- 保留串行准备。锁等待已与主线程解耦；这组负载尚不足以证明复杂的准备队列、截止时间和
  独立结果提交协议值得引入。未来若实际多分屏持续负载显著超预算，再以本轮字段定位。
- 保留 CoreText 与现有脏行/run 缓存。未命中排版累计远小于整体准备耗时，直接绕过 CoreText
  不是当前数据支持的优先项；未新增另一层行缓存。
- 保留按需图集扩容。大图集并不消除后续扩容，而预先同时放大灰度和彩色图集会付出常驻内存成本。
  CPU grow 与 GPU upload 已分别计量，可按真实字体和输出量继续评估。
- 保留辅助线程和每排版器 CF 释放线程。测得投递 p95 为微秒量级，没有证据表明共用一个释放队列
  能改善本轮响应；也没有仅为了减少线程数而把其他工作塞回帧回调。
- 不增加 250ms display link 保活。两组输入探针均匹配 200 个样本，静止/动画中位数约
  46.82/45.68ms，p95 约 49.64/49.63ms；分别有 2/4 条 trace 丢失，仅供观察。
  这既不能证明物理按键延迟，也不足以支持“空闲必然多一整帧”的判断。

[机器可读汇总](2026-09-27-window-responsiveness.json)包含完整分布与各轮原始目录。
最终定向记录按 surface 分文件保存在四个同名前缀的 `*.json.gz` 中，内容为文件名到 CSV 文本的映射；
它们不含终端内容、键码或输入文本。

## 回归结果

- 当前实现完整原生回归：361 项测试、47 个 suite 通过。
- 窗口定向回归：8 项测试（包括参数化用例）通过，涵盖三种混合模式、1/2 帧延迟偏好、
  真实跨窗口移动、关闭、缓存、截图、PTY 输出合并、光标与 Kitty 动画。
- Zig 定向回归：121/121 通过，72/72 构建步骤成功。
- trace 汇总器：7/7 通过，新增用例验证必须有回显确认、对应内容修订以及非零呈现时间才能匹配探针。
- SwiftLint strict、Zig 格式、scope/config bridge、版本一致性与 Git 空白检查通过。
- 新增的颜色检查沿用 Display P3 → sRGB 转换后比较，未放宽现有红色阈值。
  非阻塞 trace 本来允许丢弃；测试保留内容合并与序号断言，日志丢失单独报告，不要求遥测零丢失。

非测试版 `macos/build/ReleaseLocal/cghostty.app` 构建成功，版本 0.3.9／构建 29；
arm64、资源、签名与版本校验通过。未替换已安装应用，未生成发行 ZIP 或发布。
