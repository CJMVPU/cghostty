# 完整终端帧时钟验证（2026-09-27）

本轮按用户要求执行软件侧验证；外接显示器、高速摄像和能耗明确不测，不作为失败或通过项目。
版本保持 0.4.0 / 构建 30。对照基线为 `ad85cd1a9` 加本轮共用的 trace 与截止时间修复。
正式构建仍只有 CAMetalDisplayLink；实验变体由 ReleaseLocal 编译条件隔离。

## 范围与口径

- 同一台 macOS 27.0 (26A428) Apple Silicon Mac，内置 ProMotion 屏，窗口报告最高 120Hz。
- 正常 LaunchServices 启动的应用进程，前台有焦点的 800×480 窗口；没有 XCTest 测量宿主。
- 使用真实 SurfaceView、PTY、终端解析器、字形/纹理和窗口 Metal 4 合成器。
  实验窗口直接承载 SurfaceView，没有普通窗口控制器的搜索栏、滚动条或玻璃背景；不等同完整 UI 交互验收。
- 每阶段 PTY 有确定的就绪标记，预热 1 秒，再等窗口时钟静止；输入/滚轮/nvim 间隔为 16ms。
  空闲后输入逐次等时钟暂停，静止观察为 2 秒。记录前台失活并排除无效轮次。
- 探针从 Surface 输入入口发送，到 PTY 回显被解析后对应版本的 drawable `presentedTime`。
  它不等于物理键盘到屏幕发光，也不覆盖 IME 候选窗口的同步体验。
- 长呈现间隔：连续活动区间相邻正呈现时间超过 1.5×8.33ms，排除中间明确暂停的区间。
  这是时序统计，不直接称为 GPU 掉帧；trace 丢失可能影响分母或形成表观长间隔。
- `window_prepare` 包含分屏更新与绘制编码。晚取实验把提前的 CPU 准备加回总量，不隐去工作。
- A/B/A/B 初筛每输入场景 200 个探针；随后关键场景扩到 1000 个。
  相同 Metal 4 队列、最终合成、纹理与请求帧率，仅按变体改变指定因素。

## 实验发现并修复的调度问题

最初 NSView 的一轮在启动后无法静止，约 16 秒记录 1925 次回调。
`nextDrawable` 等待约一个周期后，原逻辑看到超过 target 时间就强制再画一帧，
即使内容与动画已经不再变化，仍持续触发下一帧。
修复后错过截止时间只累计统计；真正需要的下一帧仍由内容更新、动画或明确重试驱动。
两种时钟都应用同一修复后重新对照，修复前的结果不混入主比较。

另有修复后 NSView 第一轮在测量开始前未取得前台焦点，退出并保留失败记录；
同一二进制重新启动成功。该无效启动中时钟已经正常暂停，与前述循环不同。

## 3 drawable 的反例与 2 drawable 复测

NSView 3 drawable 的第二轮 nvim classic，获取 drawable 的 p99 为 8.309ms，最大 15.316ms；
晚取实验也复现：classic p99 8.357ms，nvim 区域滚动 p99 8.301ms。
此时回调仍大致每 8.33ms 到达，但渲染线程在等待 drawable，回调到呈现的优势明显缩小。
因此 3 drawable 不满足预先约定的“获取 p99 小于 0.25 周期”目标。

2 drawable 的完整 200 样本轮与 1000 样本复测：

| 场景 | 首轮获取 p99 (ms) | 复测获取 p99 (ms) |
| --- | ---: | ---: |
| 连续输入 | 1.335 | 1.067 |
| 4 分屏负载 | 1.260 | 1.289 |
| nvim classic | 1.409 | 1.324 |
| nvim instant | 1.270 | 1.395 |
| nvim 区域滚动 | 1.258 | 1.339 |

2 drawable 的上述连续区间，两轮均未记录超过 1.5 周期的呈现长间隔。
1000 样本四分屏对照：CAMetal 2.222%，NSView 3 drawable 1.961%，NSView 2 drawable 0%。
这些比例受 trace 完整度与暂停识别影响，不解释为所有输出帧的物理丢帧率。

所有有效测量阶段的 renderer/GPU 失败计数为 0，全部已保存 trace 未记录 nil drawable。
所有完整矩阵的 2 秒静止阶段均为 0 回调、0 新提交。
这只验证窗口帧时钟，未测量进程总唤醒、CPU/GPU 功耗或电池消耗。

## 两个独立附加实验

### 晚取 drawable

先在各分屏门锁内消费本帧 CPU 更新，再获取 drawable，GPU 上传、内容绘制和最终合成仍复用原管线。
准备后新来的 IO 保留到下一帧，避免同帧重复重建；所有 trace 未发现同一分屏同一序号重复更新。

1000 样本连续输入中位数/p99 为 29.502/33.636ms，四分屏为 29.517/39.572ms；
同轮 NSView 基线为 29.146/33.280ms 与 28.958/33.122ms。
未观察到额外收益，也没有消除 nvim 的 drawable 等待反例，不建议仅凭此实验加入正式路径。

### 呈现反馈校正

使用最近 31 帧的同源残差 `presentedTime - targetTimestamp` 中位数，至少 5 个样本后启用。
暂停、换屏、请求帧率变化时清空，过期 generation 的回调、零呈现和异常值不进入估计。
这避免把“提交到显示延迟”加到另一个时间基准上。

在持续 nvim 动画里，绝对预测误差中位数/p95 可降到约 0.0001ms；
但整段 p99 仍约 16.667ms，包含启动收敛样本。
频繁暂停、恢复的输入与滚轮场景反复失去历史；1000 样本连续输入及四分屏的
绝对误差中位数仍约 16.67ms。它没有成为一个适用于全部按需渲染场景的统一估计方案。
实际输入延迟也没有进一步下降，不将这个经验模型直接用于正式构建。

## 帧准备和冷中文字

1000 样本四分屏的 `window_prepare` p95：CAMetal 0.796ms，NSView 3 drawable 0.819ms，
NSView 2 drawable 0.792ms，没有观察到时钟替换导致 CPU 准备显著增加。
冷字压力阶段每批生成新中文字：各变体 `window_prepare` p95 约 5.85–6.04ms，
字形光栅化每帧中位数约 2.43–2.49ms。本轮未增加预热、线程池或共享 GPU 图集。

## 按预先约定的软件口径判断

| 条件 | NSView + 2 drawable 本机结果 |
| --- | --- |
| 输入中位数改善至少 8.33ms | 达到，连续输入约 16.87ms，四分屏约 17.34ms |
| 输入 p99 不退化 | 扩大轮约 33.1–33.3ms，低于 CAMetal 的 50.0–52.8ms |
| 四分屏呈现长间隔比例不上升 | 本轮两次 2 drawable 测量均为 0；保留 trace 丢失限制 |
| drawable 获取 p99 远小于周期 | 两次主要场景约 1.1–1.4ms，低于 2.08ms 初筛目标；未记录 nil |

结论：完整终端确认了帧时钟选择能够影响约 17ms 的输入延迟；
**NSView + 2 drawable 是下一步正式替换的优先候选。**
3 drawable、晚取 drawable、简单暂停清空的反馈校正不能作为一个整体直接采用。
本轮交付是可复现的实验与共用调度修复，正式应用继续 CAMetalDisplayLink；
没有增加运行时后端开关或回退，也没有恢复 IOSurface、窗口缩放或全屏。
后续正式替换应单独收敛按需暂停/恢复时的动画时间语义，避免把持续动画的拟合结果推广到短促输入。
外接屏、光学延迟与能耗仍按用户要求排除，不把缺少这些结果作为继续软件工作的障碍。
