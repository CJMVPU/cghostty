# 窗口 GPU 时间线复核（2026-09-28）

历史记录：本轮比较完成后，用户决定保留 CAMetalDisplayLink 及当前延迟，并删除其他实验时钟。当前实现与验证见[渲染路径统一记录](2026-09-28-renderer-unification.md)。

本轮定位提交到呈现的等待发生在 GPU 执行前还是执行后。未切换正式帧时钟，
未调整滚动纹理、帧槽、窗口尺寸策略或 Metal 提交顺序。

## 测量口径

- 基线为 `a83f5e7ff`，加本轮窗口 GPU 计时。环境仍为本机 macOS 27、内置 ProMotion 120Hz。
- 正常启动的前台实验应用，真实终端、PTY、分屏和 nvim；实验窗口不包含普通窗口控制器的全部原生装饰。
- 三个组合各两轮：CAMetal/3 drawable/请求最高帧率；CAMetal/3 drawable/系统默认帧率；NSView/2 drawable/请求最高帧率。
- 顺序为 Metal max、Metal system、View max、Metal max、View max、Metal system。
- 每轮包含 idle、echo-idle、echo-active、mixed、vim-scroll；每个输入场景发送 200 个探针。
  每阶段预热、输入节奏、前台验证和暂停识别沿用现有实验。构建不与前台测量并行。
- 不测外接屏、物理发光时间和能耗，也不把这些缺项作为阻塞条件。

新增同源时间戳：首次窗口 commit 前的 `window_enqueue`，清屏 commit 的
`window_gpu_first`（GPU 开始/结束），末尾屏障 commit 的 `window_gpu_last`（GPU 开始/结束）。
各事件用进程内唯一窗口帧序号关联；反馈即使晚于阶段结束也归回原帧所在阶段。
反馈持有弱 surface 引用，不延长已关闭的会话寿命。

- `enqueue_to_gpu_start_ms`：首次提交前到首段 GPU 开始，包含队列/drawable 等待和调用开销。
- `gpu_window_span_ms`：首段 GPU 开始到末段 GPU 结束，包含中间 CPU 提交间隙和 GPU 队列间隙，不能叫纯 GPU 执行耗时。
- `gpu_end_to_display_ms`：末段 GPU 完成到 drawable 的 `presentedTime`。
- `enqueue_to_display_ms`：以上三段逐帧之和。分段中位数不必相加等于总中位数。

旧的 `present_submit` 位于全部 commit 之后、`present()` 之前。GPU 可能在它之前已经开始，
不能用它代替首次提交时间计算 GPU 开始前的等待。呈现终点仍为软件时间戳，不是物理发光。

## 两轮结果

下表为连续输入场景每轮中位数的范围，单位 ms，不是合并所有样本后的分位数。

| 组合 | 首次提交到 GPU 开始 | GPU 工作时间范围 | GPU 完成到呈现 | 首次提交到呈现 |
| --- | ---: | ---: | ---: | ---: |
| CAMetal，最高帧率 | 0.559–0.625 | 0.459–0.521 | 40.215–40.247 | 41.395–41.408 |
| CAMetal，系统默认 | 0.580–0.625 | 0.491–0.517 | 40.227–40.257 | 41.350–41.387 |
| NSView，2 drawable | 0.675–0.744 | 0.448–0.718 | 22.776–23.180 | 24.496–24.507 |

四分屏 mixed 中，CAMetal 最高帧率的 GPU 完成到呈现为 40.127/40.160ms，
系统默认为 40.149/40.105ms，NSView 为 22.201/21.765ms。
nvim 区域滚动也出现同方向差异：CAMetal 最高帧率为 39.665/40.014ms，NSView 为 22.168/21.402ms。

连续输入探针到对应内容呈现的中位数 / p99：

| 组合 | 第 1 轮 | 第 2 轮 |
| --- | ---: | ---: |
| CAMetal，最高帧率 | 45.779 / 56.241 | 46.190 / 54.060 |
| CAMetal，系统默认 | 45.912 / 53.129 | 45.940 / 54.501 |
| NSView，2 drawable | 29.001 / 36.142 | 28.574 / 37.828 |

系统默认的活动回调间隔中位数仍约 8.33ms；在此次前台环境中，没有证据表明
不显式设置帧率范围造成了固定 41ms 延迟。它不保证所有屏幕和系统状态都选择相同刷新率。
六轮 idle 阶段均无新帧时钟回调或提交；不把它等同于进程零唤醒或低能耗结论。

## 可得结论与限制

1. 此次约 41ms 的大头明确出现在 GPU 工作完成之后。GPU 执行前的排队和终端绘制本身不能解释主体差值。
2. 相同窗口合成器与滚动缓存下，NSView 组合主要减少的是 GPU 完成后的呈现等待，约 17ms。
   本轮对比同时使用 NSView 和 2 drawable；单独替换时钟的归因参考上一轮 NSView/3 drawable 对照。
3. 可以定位到 GPU 完成后的系统呈现链路，但不能继续断言全部由 WindowServer、特定缓冲深度或面板造成。
   此次不具备区分这些内部阶段或物理扫描输出的证据。
4. 不需要因该结果删除滚动历史纹理、重写 GPU 合成或恢复 IOSurface。正式替换仍需收敛动画取样时间语义。

30 个有效阶段共记录 14,976 次窗口首次提交，14,486 条完整有效呈现时间线；
45 条缺少反馈/呈现记录，445 条完整反馈对应 `presentedTime == 0`，时间顺序异常为 0。
零呈现样本单独排除，不能填成零延迟，也不能直接等同物理丢帧。
全过程 trace 写入丢弃 230 条。共发送 3,600 个输入探针，trace 中保留 3,599 个，
3,598 个匹配到内容呈现。所有有效阶段 renderer/GPU 失败计数为 0。
以上缺失会影响尾部分位数和样本选择；本轮是本机受控复核，不是无丢失的普遍保证。

完整逐轮数据、二进制 SHA-256 见 [统计 JSON](2026-09-28-window-gpu-timeline.json)，

  首次超时原因尚未确定，不能宣称已修复该偶发失败。
