# CI Metal 诊断与 0.2.8 验证（2026-09-24）

版本更新：0.2.7 / build 17 → 0.2.8 / build 18。Zig 清单、三个应用构建配置及 release notes 同步；不修改测试目标自己的版本。

## 实际 CI 证据

- [0.2.6，运行 35951715998](https://github.com/CJMVPU/cghostty/actions/runs/35951715998/job/107503048499)：核心测试和 PCRE2 测试成功，原生 `completedFramesAdvanceThumbnailRevisionAndMetadataSkipsImages` 在 `SurfaceBridgeTests.swift:100` 超时，信息为 `No completed terminal frame`。
- [0.2.7，运行 35957218881](https://github.com/CJMVPU/cghostty/actions/runs/35957218881/job/107503004036)：同一首帧测试超时，Kitty 图片测试也在 `SurfaceBridgeTests.swift:134` 超时，信息为 `Image frame did not complete`。
- 两次运行均在首帧用例开始时记录 `metal warmup shader init failed err=error.MetalFailed`，随后等待期间持续记录 `renderer_thread: error drawing err=error.MetalFailed`。这证明有绘制尝试，不能解释成仅因空闲光标而没有触发重绘。
- 当时创建 `MTL4Compiler` 的代码在返回 nil 时直接返回通用错误，未输出对应 NSError。旧日志没有 GPU 型号或 Metal 4 能力，所以具体设备限制或驱动错误尚不能从旧日志定论。
- 现有工作流已经在 `always()` 条件下上传日志和 xcresult，两次失败运行的上传步骤均成功。本轮保留该机制，增加可读摘要而非重复上传。
- 测试计划已关闭目标并行；本轮给相关套件补充 `.serialized` 明确其内部约束，但不把并行视为已确认根因。

Apple 的 [编译器创建接口](https://developer.apple.com/documentation/metal/mtldevice/makecompiler(descriptor:)) 说明失败时返回 nil 并通过 NSError 提供原因。GitHub 的 [macOS larger runner 文档](https://docs.github.com/en/actions/reference/runners/larger-runners#available-macos-larger-runners-and-labels) 将 GPU 硬件加速列在 XLarge 规格中；安装 Metal 编译工具不等于运行时设备具有 Metal 4 能力。本轮按用户选择保留现有 `xcode-27` runner，不改用收费规格。

## 修复边界

- 两项真实 GPU 测试以运行时默认设备的 Metal 4 支持为前提。没有设备或明确不支持时，由 Swift Testing 标记为 skipped；支持 Metal 4 时继续创建真实编译器，创建失败不能转为跳过。
- 两项 GPU 测试明确设置视口尺寸。首帧测试先注入终端输出、等待文字出现，再等待相对于输出前版本的新帧，不借助强制焦点或空闲闪烁。
- 超时诊断增加当前/期望帧版本、渲染健康、核心尺寸、窗口可见性和焦点。终端文字等待失败立即抛出，避免继续产生误导性后续断言。
- 核心输出 Metal 编译器的底层 NSError，错误描述使用 UTF-8。
- CI 保存 GPU 型号、Metal 4 支持与编译器创建结果；解析 xcresult，向 job summary 写入失败断言、跳过测试和原因。原始 JSON、日志、结果包仍统一保存在 `cghostty-ci-diagnostics`。
